T+00:04 · Staging

Every mission flies the same four stages

A cheap optimizer sweeps the whole search space, real-world launch limits prune it, a numerical propagator re-flies only the survivor, and a machine-readable report says whether it held.

1 · Search

pykep + pygmo

Patched-conic Lambert arcs and gravity-assist sequences, swept by population optimizers. Multi-basin multistart optimizes every distinct porkchop valley instead of shrinking onto one.

2 · Constrain

Rocket + launch site

Vehicle C3-vs-payload curves and the site's reachable declination enter the fitness. Daily launch windows respect range-safety azimuth corridors, and every number cites its source.

3 · Verify

tudatpy + scipy

Adaptive RKDP8(7) N-body propagation with dense-output event location. Parking orbit → TLI/TMI under J2, Newton and B-plane targeters close the gap to the real trajectory.

4 · Report

Verification JSON

Every run writes a schema-validated report: step convergence, conservation, residuals, the force model actually used, and a pass/fail per check.

throughout Thousands to millions of independent candidates per run are batched into vectorized array ops — CuPy on a GPU, numpy otherwise, one code path (orbitopt.core.gpu).

Measured, not assumed

Speedup grows with batch size — GPU kernel-launch overhead dominates at small N, so a batched routine only pays off once the batch is large enough to amortize it. That threshold is measured per-routine.

T+00:27 · Systems

Three layers, one scene format

Reading and viewing a scene someone already computed doesn't need pykep, pygmo, or tudatpy — the package is split so that's true in practice, not just in principle.

01 · base install

Scene format

pip install orbitopt — stdlib + jsonschema only. read_scene / write_scene / validate_scene against a versioned, independent JSON Schema.

02 · +viewer extra

3D viewer + Mission Control

pip install orbitopt[viewer] — real PyPI wheels (numpy, PyVista, PySide6). Opens any scene file, yours or a colleague's.

03 · conda environment

Compute stack

pykep + pygmo + tudatpy ship only on conda-forge/tudat-team. Fully pinned conda-lock files build it: envs/cpu.conda-lock.yml, or envs/gpu.conda-lock.yml with CuPy on CUDA 13.

T+00:35 · Anomaly log

Bugs that cost real debugging time

Root-caused and measured, not smoothed over. Longer write-ups for the early ones live in docs/engineering-notes.md.

01
pygmo · silent 15× slowdown

Attach bfe before wrapping. It has to go on the raw UDA (uda.set_bfe(bfe)) before pg.algorithm(uda). Attaching it after silently falls back to evaluating one candidate at a time — ~15× slower, no error raised anywhere.

02
SPICE · frame mismatch

J2000 ≠ ECLIPJ2000. They're related by Earth's ~23.4° obliquity and aren't interchangeable — mixing states queried in one against the other silently produces errors of hundreds of thousands of km.

03
RK4 · step size at close approach

Fine for a coast, not for a flyby. A 600s step reported an 81,733 km closest lunar approach for a trajectory whose true, converged (≤15s step) closest approach was 4,379 km.

04
Mars TCM · aimed at a point, not a periapsis

The 2020 replay flew below the surface of Mars. The correction burn aimed the spacecraft at a point 3,889.5 km from Mars's center at a fixed time. Gravity bends the approach inward, so the real periapsis came out at 3,341 km, under Mars's 3,389.5 km radius, and the report still passed. A second targeting stage now solves for the B-plane vector with the arrival time held fixed, and the flown periapsis lands at 504.7 km altitude.

05
Verification report · two values of one constant

An energy drift that wasn't there. The orbit-insertion conservation check computed energy with SPICE's Mars GM while tudat integrated with its own, 1.9×10⁻⁸ apart. On an e = 0.75 capture orbit that reads as a 1.2×10⁻⁷ drift, which failed every run. The tell: angular momentum, which doesn't involve GM, drifted only 10⁻¹³. With the integrator's own GM the drift is 2×10⁻¹².

T+00:42 · Go / No-go

From a YAML file to a verified mission

No source edits: describe a mission's orbit elements, spacecraft, and optimizer settings, then validate and run it from the command line.

flight-terminal — orbitopt 
# view any scene -- no conda, real PyPI wheels only
pip install orbitopt[viewer]
orbitopt view solar-system

# describe a mission -- no source edits
cat my_mission.yaml
mission:
  id: my-geo-mission
  title: My GEO raising campaign
  kind: geo-raising
target:
  geostationary_longitude_deg: -101.0
campaign_search:
  n_burns: { min: 2, max: 6 }
output:
  scene_file: scenes/my-geo-mission.json

# schema-check, then optimize + tudatpy-verify + write scene and report
orbitopt validate my_mission.yaml
orbitopt run my_mission.yaml
orbitopt view scenes/my-geo-mission.json

# daily launch windows from KSC along the Mars 2020 departure asymptote
orbitopt launch-window ksc --rla 9.6 --dla 23.4 --epoch 2020-07-30 --azimuth 90 115

Every field falls back to the real GOES-16 numbers if omitted — the minimal config just re-derives the built-in mission. See the full config schema on GitHub.
